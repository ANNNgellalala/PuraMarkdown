# PuraMarkdown 渲染性能问题分析（2026-11-06）

> 触发场景：运行 `samples/PuraMarkdown.Demo`，点击"开始流式"后出现明显卡顿，极端情况下窗口/系统无响应。
> 结论：**存在架构级性能缺陷（P0）**。缺陷不在 Markdig 解析本身，而在"流式渲染在 UI 线程同步执行 + 尾部块全量重建 + 首次初始化尖峰 + 逐次全量字符串复制"。
> 说明：本报告为修复前的定位记录；修复结果见 [渲染性能修复记录](15-渲染性能修复记录.md)。

---

## 1. 复现与测量结果

测量环境：本机 i7-12700F / .NET 10.0.14 / Debug 构建 / Avalonia 12.1.5。
工具：`samples/PuraMarkdown.Spike` 新增诊断模式（直接调用同一套流式接口）。

### 1.1 Demo 同款文本（约 2.5KB，41 次 Append）

| 运行 | 总耗时 | p50 | p95 | max |
| --- | --- | --- | --- | --- |
| 第 1 次（冷启动） | **310ms** | 0.47ms | **34ms** | **88ms** |
| 第 2 次（同进程、已预热） | **7.6ms** | 0.05ms | 0.46ms | 0.66ms |

结论：**卡顿尖峰几乎全部来自首次使用的初始化（JIT / 正则编译 / Mermaid / JsonSchema / 字体与渲染管线）**，而不是每次追加的稳态成本。首次流式期间 41 次追加里夹着 5 次 30–90ms 的阻塞，全部发生在 UI 线程 → 用户看到"一顿一顿"甚至"无响应"。

### 1.2 长代码块（14.3KB，896 次 Append）

| 配置 | 总耗时 | p50 | p95 | max |
| --- | --- | --- | --- | --- |
| 启用 ColorCode 高亮 | **2977ms** | 3.2ms | **5.2ms** | 130ms |
| 关闭高亮 | **231ms** | 0.2ms | 0.3ms | 33ms |

结论：**流式过程中每次追加都会对整个未闭合代码块重新高亮**，成本随块大小线性增长；代码块越长，单次 Append 越慢。14KB 时 p95 已 5ms，100KB 代码块估算 30–50ms/次，且总追加次数随文本增长 → UI 线程被持续占满。

### 1.3 随文本长度增长的隐患（代码审计结论）

- 每次 `Append` 都执行 `_text.ToString()`（`Streaming.cs:130/148/169`），复制**全部已接收文本**；
- 每次 `Append` 都重新解析并重渲染**整个尾部窗口**（`Streaming.cs:219` → `PuraMarkdownView.cs:118-151`）；
- 因此总工作量约为 **O(n²)**（n = 文档长度），1MB 消息按 16 字符追加 = 6.5 万次 → 数十 GB 级字符串复制 + 尾块重复渲染，必然长时间占满 UI 线程。

## 2. 渲染过程拆解（一次 Append 实际发生了什么）

```
Demo Timer(40ms) → session.Append(16 chars)
  ├─ _text.Append(delta); text = _text.ToString()          ← 全量复制（O(total)）
  ├─ StreamingBlockScanner.FindStableBoundary(text, offset) ← 扫描尾部
  ├─ 若有稳定前缀：Markdig.Parse(window) → Sanitize → 渲染每个稳定块 → 追加控件
  ├─ 尾部：Markdig.Parse(tail) → Sanitize → 删除旧尾部控件 → 重新渲染尾部所有块
  │    ├─ 代码块：ColorCode 重新高亮整块（O(tail)）
  │    ├─ Mermaid：Mermaider 重新解析整段源码（首次初始化极慢）
  │    ├─ pura-agent：JSON 解析 / Schema 校验（首次初始化）
  │    └─ 其他块：重新创建控件
  └─ 控件树变更 → ScrollViewer/StackPanel 重新 measure/arrange → 渲染整窗
```

关键观察：

1. **同步执行在 UI 线程**：`Append` 内部完成解析、渲染、控件替换、布局失效；Demo 的 `DispatcherTimer`（`Program.cs:170`）直接调用，没有后台线程、没有合帧、没有背压。
2. **尾部块全量重建**：`AppendStreamingDocument(tail, ..., isTail: true)` 先 `RemoveTailRecords()` 再重新渲染尾部所有块（`PuraMarkdownView.cs:118-151`）。只要最后一个块未闭合（代码块、表格、列表、Mermaid、`pura-agent` JSON），每次追加都把整个块重建一遍。
3. **高亮/图表/JSON 无缓存**：`CodeBlockRenderer` 每次渲染都调用 `ICodeHighlighter.Highlight(整段代码)`（`CodeTableDiagramRenderers.cs:73-77/127`）；Mermaid 每次重解析；组件 JSON 每次重解析。
4. **首次初始化全在 UI 线程**：ColorCode 的 C# 正则首次编译 ~90ms；Mermaider 首次解析 ~50ms；JsonSchema.Net 首次校验 ~35ms；另有 JIT 与首次字体/布局路径。首次点击"开始流式"必然出现 0.2–0.5s 的累计阻塞（慢机/Release 差异可能更大）。
5. **每 tick 重新设置 `Background` 为新 Brush**（`PuraMarkdownView.cs:252`），触发视觉失效；量级小，但属于不必要的分配。
6. **无虚拟化**：`StackPanel` 承载全部块，每次追加都使容器 measure 失效；长对话/长消息下布局成本随块数增长。
7. **`CompleteAsync` 再做一次全量解析 + 全量重建**（`Streaming.cs:152`），完成瞬间可能有一次明显卡顿（本次文本小，未单独测量）。

## 3. 缺陷分级

| 级别 | 缺陷 | 证据 | 影响 |
| --- | --- | --- | --- |
| **P0-1** | 流式路径完全同步跑在 UI 线程，无合帧/背压/后台解析 | `Streaming.cs:130-219`；Demo `Program.cs:197-198` | 任何单次 Append 慢都会直接卡 UI；连续追加时消息泵饥饿 |
| **P0-2** | 每次追加重建整个尾部块（含未闭合大块） | `PuraMarkdownView.cs:118-151` | 长代码块/表格/列表时 O(tail)/tick，整体 O(n²) |
| **P0-3** | 每次尾部重建都重新执行高亮/Mermaid/JSON | `CodeTableDiagramRenderers.cs:73-77`；Mermaid renderer；AgentComponentRenderer | 长代码块实测总耗时 2977ms vs 231ms（12.9×） |
| **P0-4** | 每次 Append 全量 `_text.ToString()` | `Streaming.cs:130/148/169` | 长消息 O(n²) 复制与 GC |
| **P1-1** | 首次使用初始化（正则编译/JIT/Mermaid/JsonSchema/字体）在 UI 线程 | 实测首次 310ms vs 预热后 7.6ms | 首次点击"开始流式"必卡 0.2–0.5s，慢机更差 |
| **P1-2** | 无块级虚拟化，容器每次 measure 全部子块 | `PuraMarkdownView.cs` 的 StackPanel | 长消息布局成本随块数增长 |
| **P1-3** | 每次渲染新建 `SolidColorBrush` + 控件/文本 Run | `PuraMarkdownView.cs:252`；`CodeBlockRenderer` | GC 压力、视觉失效 |
| **P2** | Demo 采用 Debug、40ms 定时器、16 字符/次，未做预热 | `samples/PuraMarkdown.Demo/Program.cs` | 放大 P0/P1 的表现 |

## 4. 为什么会出现"整机无响应"

1. UI 线程被连续占用（首次初始化尖峰 + 尾部重渲染 + 布局），Windows 消息泵得不到调度；阻塞累计超过系统阈值时窗口标记"未响应"。
2. 若一次尾块很大（如 100KB 代码块 + 高亮），单次 Append 可达几十到数百毫秒，40ms 定时器反复触发 → 持续接近 100% 单核占用。
3. 长消息（Demo 之外的场景）触发 O(n²) 复制/渲染，可能演变为秒级甚至分钟级阻塞。
4. Markdig 本身不是瓶颈：14KB 文档一次解析仅百微秒级（见 `docs/13` 基准）；问题在于"解析+渲染的次数与线程模型"。

## 5. 修复方案（建议，尚未实施）

### 5.1 必须（P0，1.0 前）

1. **后台解析 + UI 线程嫁接 + 合帧调度**
   - `Append` 只入队（Channel/Interlocked），解析/扫描/高亮在后台线程；UI 线程每 16ms 最多应用一次 Patch。
   - 适配器只 graft 变化块，禁止每 tick 全量 measure。
2. **尾部块增量更新，而不是重建**
   - 用 `IIncrementalPuraRenderer.Update(existing, newNode)`；
   - 代码块增加 `CodeBlockView.Update(code)`：只更新 `TextBlock.Text`/增量高亮 Run；
   - 未闭合大块（代码/表格/Mermaid）先显示占位或纯文本，闭合/稳定后再渲染重型内容。
3. **去掉全量 `_text.ToString()`**
   - 维护 `StringBuilder committed + tail`；扫描器保留跨次状态（是否在围栏内、最后稳定行），只处理新增字符。
4. **高亮/图表/JSON 缓存与节流**
   - 按 `(language, codeHash, theme)` 缓存高亮结果；
   - 流式中代码块只在"稳定"后高亮一次（或按 200ms 节流）；
   - Mermaid 在未闭合时显示源码占位，闭合后再调用引擎。
5. **首次初始化预热**
   - 应用启动后在后台预热 ColorCode 语言、Mermaider、JsonSchema 与常用字体；
   - 或首次渲染前显示 skeleton，避免把初始化放在用户点击时。

### 5.2 应该（P1）

6. **块级虚拟化**（`ItemsRepeater`/`VirtualizingStackPanel`）与固定/估算块高。
7. 复用 Brush/控件样式；减少每 tick 分配。
8. `PuraRenderScheduler` 真正落地（设计文档已定义，代码未实现）。

### 5.3 Demo 侧缓解（不改框架也能先验证）

- 用 **Release** 构建运行；
- 定时器降到 80–100ms、每次 32–64 字符；
- 点击前先"预热"一次（隐藏渲染一遍或后台初始化）；
- `Append` 改为 `Dispatcher.Post` + 合并。

## 7. 结论

- **是严重性能缺陷**，且是架构层的（线程模型 + 尾块重建 + 无缓存/无合帧），不是 Demo 写法或 Markdig 解析问题。
- 短消息表现为首次 0.2–0.5s 的连续卡顿；长代码块/长消息会放大为秒级冻结，确实可能让用户感觉"电脑无响应"。
- 建议把 **P0-1 ~ P0-4** 列为 1.0 发布前的阻断项；修复后以"追加 P95 ≤16ms、max ≤50ms、100KB 代码块流式无冻结"作为验收基线。
