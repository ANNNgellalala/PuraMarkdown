# 讨论：IR / 虚拟渲染树 / 多平台适配是否进入实现计划（2026-11-05）

> 背景：v0.3 已按需求方案定为 **Markdig AST 直连 Avalonia 控件**（ADR-0011/0016）。你提出重新讨论三块被移除的设计——IR、虚拟渲染树、多平台适配——是否要加回实现计划。
> **决策结果（2026-11-05，用户选定选项 A）**：**1.0 三项都不加**，只做 3 个"未来预留钩子"，并保留触发条件与回补成本。ADR-0020/0021/0022 已从"提议"改为"已接受"。本文保留完整分析，作为未来触发时的评估依据。

## 0. 一句话结论

| 部分 | 1.0 是否实现 | 决策 | 触发条件（满足才加） | 回补成本 |
| --- | --- | --- | --- | --- |
| IR（文档模型） | ❌ 不实现 | 保留 Markdig AST；加"AST 净化 pass"补上安全集中点 | 出现非 Avalonia 渲染后端 / 服务端无 UI 渲染 / 高保真导出 / 节点级缓存 | 3–4 周 |
| 虚拟渲染树（RenderNode + diff） | ❌ 不实现 | 用 Avalonia 视觉树 + 块级记录（`BlockRecord`） | 需要平台无关的渲染快照 / 块内细粒度增量 / 多后端 | 2–3 周 |
| 多平台适配层 | ❌ 不实现 | 跨平台交给 Avalonia（Win/macOS/Linux）；平台差异收进少量服务接口 | 需要 Blazor/原生 MAUI/无 Avalonia 的宿主 | 3–4 周 |
| —— 未来预留钩子 | ✅ 实现（约 2–3 人日） | `IAstSanitizer`、`IPuraPlatformServices`、`BlockRecord`（源码 span + hash） | — | — |

## 1. IR（文档模型）：为什么 1.0 不需要

### 1.1 IR 能买到什么

| 收益 | 当前是否已被替代 |
| --- | --- |
| 渲染确定性的测试基线 | 已有替代：无头 Avalonia + 控件树确定性 dump（golden） |
| 安全过滤的集中点 | 部分缺失：目前分散在默认渲染器；可用一次 AST 净化 pass 补上（成本 < 1 人日） |
| 导出 HTML/文本/Markdown | 可直接对 Markdig AST 写 visitor（`PuraMarkdown.Export`），不需要 IR |
| 与 Markdig 版本解耦 | 1.0 锁 1.5.1，插件直接用 Markdig 节点；IR 只会在升级时多一层适配，不会减少升级工作量 |
| 节点级 diff / 缓存 | 块级源码 hash 已够用；节点级收益要等"块内超大内容"真实出现 |
| 多平台/服务端渲染 | 1.0 只做 Avalonia 桌面，不需要 |
| 可序列化文档 | Markdown 原文本身就是可序列化载体；缓存原文即可 |

### 1.2 IR 的成本（v0.2 已实测过一遍）

- **多一层映射**：AST→IR→Control，三套类型、三套测试、三处语义漂移（v0.2 的评审报告已暴露这类成本）；
- **插件学习成本**：插件作者要同时理解 Markdig 节点与 Pura IR；
- **同步问题**：IR 与 Markdig AST、IR 与控件树双向同步，流式场景尤其容易出错；
- **工期**：按 v0.2 经验，IR 本身（模型 + 构建器 + 遍历 + 快照 + 测试）约 **3–4 周**，且会推迟 M1/M2。

### 1.3 建议：不建 IR，但补一个"净化 pass"

```
Markdig AST
   → IAstSanitizer.Sanitize(document)     // 一次遍历：HTML 节点标记、URL 标记、超限标记、诊断
   → 分发/渲染（默认渲染器读取标记；插件渲染器通过 RenderContext 读取同一结论）
```

- 作用：把"安全/合规判定"从各渲染器收敛到一次遍历，插件无法绕过（与 IR 的收益接近，成本极低）。
- 复杂度：< 1 人日；不需要新模型。
- 后续若要 IR：这个 pass 就是 IR 构建器的雏形，可直接升级。

### 1.4 什么情况下加回 IR

满足任意两条即触发立项：
1. 出现**第二个渲染后端**（Blazor/HTML/MAUI 原生），且不是 Avalonia；
2. 需要**服务端/无 UI 渲染**（生成 HTML/PDF/邮件）且要求与 UI 一致；
3. 需要在**节点级**做缓存/引用计数/跨会话复用（而非块级）；
4. Markdig 发生 breaking 升级，且无法通过适配层解决，需要"锁在自有模型"。

## 2. 虚拟渲染树（RenderNode + diff）：为什么 1.0 不需要

### 2.1 它能买到什么

| 收益 | 当前实现 | 是否足够 |
| --- | --- | --- |
| 平台无关的渲染快照 | 无（控件树 dump 是测试用途） | 1.0 单平台，足够 |
| 细粒度增量（节点级） | 块级替换 + `IIncrementalPuraRenderer` | 流式场景足够；块内超长内容才可能不足 |
| 多后端渲染 | 无 | 1.0 不需要 |
| 布局/主题与控件创建解耦 | 主题 token 已解耦样式；控件创建仍直接 | 可接受 |

### 2.2 成本与副作用

- 插件从"返回 Avalonia 控件"变成"返回 RenderNode"，**失去直接使用 Avalonia 的能力**（自定义绘制、动画、第三方控件、`ItemsRepeater` 能力），这正是需求方案要的"插件可产出任何 Avalonia 控件"；
- 需要维护两棵树（RenderNode + 控件树）和同步逻辑；
- diff 算法、key 稳定、样式 token 解析都要重做；
- 工期 **2–3 周**（不含调试流式边界的额外成本）。

### 2.3 建议

1.0 用 **"块级记录 + 增量嫁接"** 代替虚拟树：

```csharp
sealed record BlockRecord(
    int Index,
    int Start, int End,          // 源码 span
    ulong Hash,                  // 块源码哈希
    MarkdownObject Node,         // 本次解析的 AST 节点
    Control View);               // Avalonia 控件
```

- 追加时只比较尾部块的 hash；变化则用 `IIncrementalPuraRenderer.Update` 或替换该块控件；
- 已提交块不做任何重建 → 与虚拟树 diff 的效果等价（在块粒度上）；
- 这也是未来引入虚拟树时的天然输入（`BlockRecord` 可直接扩成 `RenderNode`）。

### 2.4 触发条件

1. 需要**非 Avalonia 后端**或**服务端渲染快照**；
2. 实测发现"块内超长内容（如数万字单段）"替换开销不可接受，需要块内细粒度更新；
3. 需要把渲染结果**序列化/跨进程传输**（例如渲染服务）；
4. 需要**虚拟化 + 结构 diff** 同时成立（当前虚拟化按块，已够）。

## 3. 多平台适配：为什么 1.0 不需要独立适配层

你已确认：**核心直接依赖 Avalonia，依托 Avalonia 的跨平台能力**（Windows / macOS / Linux；Avalonia 12 同时支持移动/WebAssembly 变体，但 1.0 不承诺）。

### 3.1 Avalonia 已覆盖的部分

- 窗口/控件/布局/输入/渲染：Avalonia 统一；
- 主题/字体：Avalonia 主题体系 + 系统字体；
- 剪贴板、Dispatcher、文件选择：Avalonia API；
- 高 DPI、多显示器、无障碍（AutomationPeer）：Avalonia 提供基础。

### 3.2 仍需隔离的"平台差异"（薄接口，不是适配层）

| 能力 | 接口 | 默认实现 | 说明 |
| --- | --- | --- | --- |
| 剪贴板 | `IPuraClipboard` | Avalonia `TopLevel.Clipboard` | 便于测试替身；移动端行为差异 |
| UI 线程调度 | `IDispatcher`（Avalonia 类型） | `Dispatcher.UIThread` | 已在 `RenderContext` 暴露 |
| 图片加载/解码 | `IImageLoader` | 不联网占位实现 | 宿主注入 HTTP/缓存策略 |
| 链接打开 | `ILinkHandler` | 不自动打开 | 宿主决定浏览器/内置视图 |
| 字体/等宽字体回退 | `PuraTheme.Typography` + 平台字体探测 | Avalonia 默认 | CJK/emoji 需要实测 |
| 无障碍播报 | `IAccessibilityAnnouncer`（可选） | Avalonia `AutomationPeer` | 读屏差异需实测 |

> 这些接口是"服务注入"，与"渲染适配层"不同：它们不抽象控件，只抽象外部能力。

### 3.3 为什么不做渲染适配层

- 1.0 的跨平台需求 = 桌面三平台，Avalonia 已解决；
- 适配层会让插件契约在"平台无关类型"与"Avalonia 控件"之间二选一：要么失去 Avalonia 能力（自定义控件/动画），要么适配层形同虚设；
- 工期 3–4 周，且每次加平台都要重写默认渲染组（v0.2 的老路）。

### 3.4 触发条件

1. 需要 **Blazor/Web** 或 **原生 MAUI** 渲染（非 Avalonia）；
2. 需要**无 UI 的渲染服务**；
3. Avalonia 在目标平台出现不可接受的限制（如某平台输入法/无障碍/性能）。
此时按 ADR-0011 的备选抽"平台无关渲染描述"，Adapter 层在 3–4 周内补齐。

## 4. 现在就要做好的 3 个"未来预留钩子"（低成本、无返工）

| 钩子 | 现在实现 | 未来收益 |
| --- | --- | --- |
| `IAstSanitizer` 净化 pass | 一次 AST 遍历，标记 HTML/URL/超限，产出诊断 | 安全集中点；未来 IR 构建器的雏形 |
| `BlockRecord`（span + hash + node + view） | 流式与增量嫁接已需要 | 未来虚拟树/IR 的输入；块级缓存 |
| `IPuraPlatformServices`（剪贴板/字体/播报） | 薄接口 + 默认实现 | 未来适配层只需实现服务，不动控件 |

> 工作量合计约 **2–3 人日**，放进 M0。

## 5. 如果现在就加：总代价与影响

| 组合 | 新增工期 | 对 1.0 的影响 |
| --- | --- | --- |
| 只加 IR | +3–4 周 | 插件要学两套模型；M1/M2 顺延；测试改为 IR + 控件双基线 |
| 只加虚拟树 | +2–3 周 | 插件不再返回 `Control`，Avalonia 能力受限；与需求方案冲突 |
| 只加适配层 | +3–4 周 | 1.0 只交付 Avalonia，适配层空转；默认渲染组要抽象化 |
| 三者都加 | **+8–10 周**（接近 v0.2 的 70–95 人日） | 回到 v0.2 架构，提案的"轻量只读控件"定位丢失 |

**决策（2026-11-05，选项 A）：1.0 都不加，保留钩子（+2–3 人日）。** 如果未来目标是"2.0 做多平台/服务端渲染"，建议届时只先加 IR（不改插件契约，逐步双轨），其余两项等真实需求。
