# ADR-0004：流式渲染采用「稳定块提交 + 尾部窗口重解析」

- 状态：**被 ADR-0015 取代**（2026-11-05：改为块级脏检查 + 尾部窗口 + 视觉树嫁接；保留尾部窗口结论）
- 日期：2026-11-04

## 背景

LLM 逐 token 输出。若每次增量都全文重解析：

- 解析开销 O(n²)，长回答不可接受；
- UI 整篇重排，滚动跳动、代码高亮重算；
- 未闭合语法导致 AST 抖动。

候选：

1. 全文重解析 + 虚拟 DOM 全量 diff（简单，但性能差）；
2. 稳定块提交 + 尾部窗口重解析（块级增量）；
3. 接入真正的增量解析器（Markdig 不提供，需 fork）。

## 决策

采用方案 2，并保留方案 1 作为兜底开关（`StreamingOptions.ForceFullReparse`，用于极端 case 或调试）。

## 方案要点

- 块边界由 `StabilityClassifier` 判定：围栏未闭合、容器未闭合、表格未确认结束、列表可能延续 → 进入尾部窗口。
- 尾部窗口按字符计 8–16 KB（`TailWindowChars`），在最近空行强制提交；窗口重解析成本与文档总长无关。
- 稳定块仅解析一次，节点 ID 由"内容哈希 + 结构路径"生成，追加时既有 ID 不变 → 适配器复用实例。
- 文档级引用表（链接引用定义/脚注）增量维护 + 每帧预扫描；已提交块不回溯，`Complete()` 时全量校正。
- 流式期间交互默认禁用；`Complete()` 后校正。
- 展示层单独处理 partial inline（未闭合 `**`/`` ` ``/`[`）：延迟一帧或补全，仅影响尾部。

## 实测依据（Markdig 1.5.1）

- Markdig **没有增量解析 API**（入口只有 `string`，issue #489 官方确认；issue #858 仍 open）。
- 44.7 KB 文档整篇解析约 12.3 ms；**每 1 KB 增量全文重解析约 6.25 ms/次，只解析尾窗口约 0.02 ms/次（差约两个数量级）**。
- 未闭合围栏代码块是"隐式闭合"的（安全）；未闭合 `:::` 会把后文吞入容器（必须靠窗口规避）；未闭合强调/反引号/链接显示为字面量。
- 表格缺少 `|---|` 分隔行会退化为段落 → 表格在流式中天然不稳定。

## 理由

- 不 fork Markdig（维护成本、许可、升级风险）。
- 方案 1 作为兜底可保证正确性：性能不达标时先保正确。
- 该策略对"前缀稳定、尾部变化"的 LLM 输出天然契合。

## 后果

- 需要 `StreamingAssembler`、`StabilityClassifier`、`PuraRenderScheduler` 三个新组件。
- 正确性依赖边界判定；必须用"逐段追加 vs 一次性解析"的等价性属性测试守住。
- 已知限制：引用链接跨窗口时可能延迟解析（低频，`Complete()` 时校正）。
