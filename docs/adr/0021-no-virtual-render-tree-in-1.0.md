# ADR-0021：1.0 不引入平台无关虚拟渲染树（RenderNode）

- 状态：**已接受**（2026-11-05 用户确认：选项 A，1.0 不引入虚拟渲染树）
- 日期：2026-11-05
- 关联：[讨论文档](../07-IR-虚拟渲染树-多平台-讨论与决策.md)、ADR-0011、ADR-0015

## 背景

v0.2 用 `RenderNode` 虚拟树 + diff/patch 作为核心与适配器的边界。v0.3 渲染器直接返回 Avalonia `Control`，块级增量嫁接替代了虚拟树 diff。用户要求评估是否加回。

## 决策

1.0 **不引入虚拟渲染树**；用 `BlockRecord { Index, Start, End, Hash, Node, View }` + `IIncrementalPuraRenderer` 实现块级脏检查与更新。

## 理由

- 需求方案要求"插件可产出任何 Avalonia 控件"；虚拟树会迫使插件返回平台无关描述，**丢失 Avalonia 能力**（自定义绘制、动画、第三方控件）；
- 块级粒度已满足流式增量：追加只影响尾部块，已提交块不重建；
- 虚拟树需要维护两棵树与同步逻辑、重做 diff/key/样式 token，成本 2–3 周；
- 当前没有多后端/服务端渲染需求，虚拟树的跨平台收益无法兑现。

## 后果

- 增量粒度为"块"，块内超长内容（如数万字单段）更新时需整块替换；已列入性能风险，M3 实测。
- 未来若引入虚拟树：`BlockRecord` 可直接扩展为节点树；渲染器契约可增加并行路径（`IPuraNodeRenderer`），不需要一次性替换现有 `IPuraRenderer`。

## 触发条件

1. 需要非 Avalonia 后端或服务端渲染快照；
2. 实测块内超长内容替换开销不可接受，需要块内细粒度更新；
3. 渲染结果需要序列化/跨进程传输；
4. 需要虚拟化 + 结构 diff 同时成立。

## 备选

现在加入（+2–3 周）：与"Avalonia 原生插件"定位冲突，不推荐；若坚持，需同时修改插件契约、默认渲染组与测试基线。
