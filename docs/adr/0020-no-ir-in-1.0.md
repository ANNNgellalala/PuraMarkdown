# ADR-0020：1.0 不引入 IR（文档模型），保留 Markdig AST

- 状态：**已接受**（2026-11-05 用户确认：选项 A，1.0 不引入 IR，只做预留钩子）
- 日期：2026-11-05
- 关联：[讨论文档](../07-IR-虚拟渲染树-多平台-讨论与决策.md)、ADR-0011、架构 §19

## 背景

v0.2 曾设计"Markdig AST → 自建不可变 IR（PuraDocument）→ RenderNode → 适配器"。v0.3 按需求方案改为 Markdig AST 直连 Avalonia。用户要求重新评估 IR 是否加入实现计划。

## 决策

1.0 **不引入 IR**，Markdig AST 即文档模型；补一个 `IAstSanitizer` 净化 pass 作为安全集中点。

## 理由

- IR 的主要收益（跨平台、服务端渲染、序列化、节点级缓存）在 1.0 没有真实需求；
- 成本高：模型 + 构建器 + 遍历 + 快照 + 测试约 3–4 周，并导致插件学习两套模型；
- v0.2 的评审已暴露"三套类型、三处语义漂移"的维护成本；
- 安全/合规可由一次 AST 遍历 + `RenderContext` 策略覆盖，接近 IR 的集中度；
- 导出（HTML/文本/Markdown）可直接遍历 Markdig AST，无需 IR；
- 渲染确定性已有替代：无头 Avalonia 控件树 dump + golden 快照。

## 后果

- 渲染器直接消费 `MarkdownObject`，插件与 Markdig 1.5.1 强绑定（锁版本 + 回归）。
- 无节点级缓存/序列化；块级 hash 与源码 span 足够当前流式与增量需求。
- 未来若需要 IR，`IAstSanitizer` 的遍历与 `BlockRecord` 是天然起点，可增量演进而非重写。

## 触发条件（满足任意两条则重新评估）

1. 出现第二个非 Avalonia 渲染后端；
2. 需要服务端/无 UI 渲染且要求与 UI 一致；
3. 需要节点级缓存/引用计数/跨会话复用；
4. Markdig 发生无法适配的 breaking 升级。

## 备选

现在加入 IR（+3–4 周）：仅建议在明确计划 2.0 多后端时采用；实施方式为"IR 与 Markdig 节点双轨"，逐步迁移渲染器，避免一次性重写。
