# Markdown 语法与渲染分离讨论（类 IDE/LSP 协作）

> 结论：**方向成立，但不应只是"拆程序集"**。若 Arc.Avalonia 要基于语法树自定义控件/样式，需要把 Markdig AST 升级为**稳定的文档语义模型**（syntax service），再让渲染层消费它。
> 这仍是"文档模型"，不是之前否决的虚拟渲染树/IR；但需要新的 ADR，并认真处理性能与 API 稳定性。

---

## 1. 当前边界

现状：

```text
PuraMarkdown（核心）
  Markdig 解析 → Markdig AST → IPuraRenderer → Avalonia Control
  ├─ 流式扫描/块复用
  ├─ 主题/本地化/虚拟化
  └─ 插件契约（Renderer/Fence/Inline/Agent）
```

- `IPuraRenderer` 的输入是 `MarkdownObject`（Markdig 类型），渲染上下文 `RenderContext` 依赖 Avalonia；
- Arc.Avalonia 若想完全自定义控件/样式，仍需依赖 Markdig AST + Avalonia + 核心流式实现；
- 语法树没有独立、稳定的公共契约；Markdig 类型变化会外溢到宿主。

因此，"渲染器可替换"已经存在，但**语法层与渲染层没有真正解耦**。

---

## 2. 三种拆分方式

| 方案 | 做法 | 优点 | 问题 |
| --- | --- | --- | --- |
| A. 只拆程序集 | `PuraMarkdown.Syntax` + `PuraMarkdown.Avalonia`，仍暴露 Markdig AST | 改动小、性能几乎不变 | Arc 仍绑定 Markdig；不是稳定协议，LSP 类比不成立 |
| B. Markdig AST 作为契约 | Syntax 返回 `MarkdownDocument` | 零转换成本 | 公共 API 被 Markdig 绑架；自定义语法/跨版本困难；无诊断/增量协议 |
| C. 语义文档模型 | Syntax 输出稳定 `PuraDocument`/节点；渲染层消费节点 | 真正解耦；可多渲染器；可做诊断/大纲/折叠 | 需要一次 AST→模型转换；性能与 API 设计成本 |
| D. 进程外 LSP 式协议 | JSON-RPC/序列化文档 | 跨进程/多语言 | 对本场景过重；延迟/部署复杂 |

**推荐 C**，D 仅在将来需要独立语言服务进程时考虑。

---

## 3. 目标架构

```text
PuraMarkdown.Syntax（无 Avalonia）
  Markdig 解析
    → 稳定文档模型 PuraDocument / PuraBlockNode / PuraInlineNode
    → 诊断、Span、Outgoing links、大纲、扩展节点
    → 流式/增量语法会话
          │
          ├── PuraMarkdown.Avalonia（默认渲染）
          │     IPuraNodeRenderer → Control
          │     PuraMarkdownView / 主题 / 虚拟化 / 交互
          │
          └── Arc.Avalonia（自定义 UI）
                自己的节点→控件映射、样式、布局、交互壳
```

### 3.1 Syntax 包职责

```csharp
namespace PuraMarkdown.Syntax;

public interface IPuraSyntaxService
{
    PuraDocument Parse(string markdown, PuraParseOptions? options = null);
    PuraDocument ParseIncremental(PuraDocument previous, PuraTextChange change);
    IPuraSyntaxStreamingSession BeginStreaming(PuraSyntaxStreamingOptions? options = null);
}

public sealed record PuraDocument(
    int Version,
    string Text,
    IReadOnlyList<PuraBlockNode> Blocks,
    IReadOnlyList<PuraDiagnostic> Diagnostics,
    PuraDocumentOutline Outline);

public abstract record PuraNode(PuraSourceSpan Span, string Kind);

public sealed record PuraParagraphNode(...) : PuraBlockNode(...);
public sealed record PuraHeadingNode(int Level, ...) : PuraBlockNode(...);
public sealed record PuraCodeBlockNode(string? Language, string Text, bool IsClosed) : PuraBlockNode(...);
public sealed record PuraTableNode(...) : PuraBlockNode(...);
public sealed record PuraExtensionBlockNode(string ExtensionKind, string Raw, object? Payload) : PuraBlockNode(...);
```

- `PuraSourceSpan`：偏移/长度，支持选中、锚点、滚动定位；
- `PuraDiagnostic`：code/severity/message/span（对应 LSP diagnostics）；
- `PuraDocumentOutline`：标题、代码块、列表等折叠/大纲信息；
- 扩展节点：自定义语法以 `ExtensionKind` + payload 表示，避免把 Markdig 类型暴露给 UI；
- 安全/预算：URL 策略、MaxBlocks/深度等在 syntax 层完成，诊断携带 span。

### 3.2 Renderer 包职责

```csharp
public interface IPuraNodeRenderer
{
    bool CanRender(PuraNode node, PuraRenderContext context);
    Control Render(PuraNode node, PuraRenderContext context);
}
```

- 渲染器注册表按节点类型/Kind 选择；
- 默认渲染器（段落/标题/代码/表格/Agent fence）在 `PuraMarkdown.Avalonia`；
- Arc.Avalonia 可注册自己的 renderer，或完全不使用默认控件，只消费 `PuraDocument`；
- `PuraMarkdownView` 变成"默认渲染宿主"，内部只依赖 Syntax + 节点渲染器。

### 3.3 流式/增量

- 当前 `StreamingBlockScanner`、块复用、尾部窗口属于**语法层**，应移入 Syntax；
- Syntax 会话输出版本化 `PuraDocument` 与 `DocumentChanged`（变更块/节点）；
- 渲染层只处理"哪些节点新增/替换/移除"，不再自己判断 Markdown 边界；
- Arc 也可独立使用语法会话做实时预览/编辑器。

### 3.4 Agent / Chat 的对应拆分

- Agent：
  - `PuraMarkdown.Agent` 目前同时含语法（fence JSON）与控件；
  - 目标：Agent 语法节点进入 Syntax 扩展层（`ExtensionBlockNode` + `PuraAgentNode`），控件渲染留在 Avalonia/Agent 渲染包；
  - 交互状态（`InteractionStates`）属于渲染/宿主层，但节点 ID 由语法层提供。
- Chat：
  - `PuraMarkdown.Chat` 再分为 **会话模型/快照/控制器**（无 Avalonia）与 **Chat Avalonia 视图**；
  - Arc.Avalonia 可复用会话模型与快照，自己实现消息列表/气泡。

---

## 4. 类 LSP 的收益

| LSP 能力 | PuraMarkdown 对应 |
| --- | --- |
| 文档同步 | `PuraDocument.Version` + 增量 `ParseIncremental` |
| 语法树/符号 | `PuraDocument.Outline`、节点树 |
| 诊断 | `PuraDiagnostic`（URL、预算、Agent JSON 错误） |
| 语义 token/角色 | 节点 Kind/属性，渲染层映射样式 |
| 自定义请求 | 扩展节点 + 插件协议 |
| 多客户端 | 默认渲染器、Arc.Avalonia、测试/工具 |

核心价值：Arc.Avalonia 不再继承/修改 PuraMarkdown 控件，而是**消费文档协议**；两个项目可以独立演进。

---

## 5. 主要代价与风险

1. **性能**：Markdig AST → 语义模型多一次遍历/分配；当前 1MB/1000 块基准会变化，需设预算并实测。
2. **API 稳定性**：`PuraDocument` 一旦公开就是长期契约，需要版本化/兼容策略。
3. **双模型维护**：Markdig AST 与语义模型并存，需保证一致；建议 Markdig 只作为 Syntax 内部实现，不对外。
4. **流式重构**：块复用/尾部窗口与渲染耦合较深，迁移风险高，需要现有测试/golden 兜底。
5. **包数量**：Syntax/Avalonia/Agent/Chat 组合增多，版本必须统一；需要元包降低宿主选择成本。
6. **与 ADR-0011 冲突**：之前"无 IR"是为了性能与简单；本方案是**文档协议层**，不是虚拟 UI 树，但仍需新 ADR 说明边界。
7. **安全**：sanitizer 从渲染层移到 syntax 层，确保所有消费者（包括 Arc）都拿到已清洗/带诊断的文档。

---

## 6. 建议的落地路径

### 阶段 1：抽出 `PuraMarkdown.Syntax`（先只读）
- 新增 syntax 包，Markdig 仍内部；
- 先为**核心节点**提供语义模型（段落/标题/列表/引用/代码/表格/链接/图片）；
- 现有渲染器逐步改为消费模型；
- Arc 可先只读语法树做大纲/工具，不接管渲染。

### 阶段 2：渲染层独立
- `PuraMarkdown.Avalonia` 只依赖 Syntax；
- `IPuraNodeRenderer` + 注册表；默认控件不变；
- Arc 可替换任意节点渲染器/样式。

### 阶段 3：Agent/Chat 分层
- Agent 语法节点入 Syntax 扩展；Agent 控件独立；
- Chat 拆模型/快照与 Avalonia 视图。

### 阶段 4（可选）：进程外协议
- 只有需要独立语言服务/多语言客户端时才做 JSON 协议，不提前设计。

---

## 7. 建议的决策

1. **采用语义文档模型（C），不直接暴露 Markdig AST**；否则 Arc 仍被 Markdig 绑定。
2. **范围限定为"文档语法 + 诊断 + 增量"**，不做虚拟 UI 树/布局树。
3. **性能预算**：以当前 1MB/1000 块基准为基线，转换开销设可接受阈值（例如首屏 +15% 内），不达标则用低分配/惰性节点优化。
4. **包命名**：`PuraMarkdown.Syntax`、`PuraMarkdown.Avalonia`；`PuraMarkdown` 作为默认元包/兼容包。
5. **先做只读语法服务**，再让默认渲染器迁移；避免一次性大爆炸重构。
6. **新增 ADR-0025**：Syntax/Renderer separation；说明与 ADR-0011 的差异（文档协议 vs 虚拟渲染树）。

---

## 8. 何时不值得做

- 如果 Arc.Avalonia 只需要换颜色/字体/少量控件，现在的 `PuraTheme` + `IPuraRenderer` 已够；
- 如果只需要"渲染后控件树"，不需要稳定语法模型，拆包收益有限；
- 如果团队无法承担流式/性能重构成本，先做阶段 1 的只读语法树即可。
